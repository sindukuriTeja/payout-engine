# EXPLAINER.md — Playto Payout Engine

## What this is

A minimal payout engine for Playto Pay: merchants accumulate INR balance from international customer payments, then withdraw to their Indian bank account. This service handles the withdrawal side — balance tracking, payout requests, settlement simulation, and all the concurrency/integrity guarantees that come with moving money.

---

## Architecture overview

```
┌─────────────┐      POST /api/v1/payouts/       ┌────────────────┐
│   React UI  │ ──────────────────────────────▶  │  Django + DRF  │
│  (polling)  │ ◀──────────────────────────────  │   (API layer)  │
└─────────────┘      JSON responses               └───────┬────────┘
                                                          │
                                           services.py    │  SELECT FOR UPDATE
                                           (critical      │  + transaction.atomic
                                            path)         │
                                                          ▼
┌─────────────┐    task dispatch           ┌────────────────┐
│   Celery    │ ◀─ on_commit ──────────── │   PostgreSQL    │
│   Worker    │                            │                │
│             │ ──── settle/fail ────────▶ │  merchants      │
│  Beat (10s) │    (SELECT FOR UPDATE)     │  ledger_entries │
└─────────────┘                            │  payouts        │
       │                                   │  idempotency    │
       ▼                                   └────────────────┘
  Simulated bank
  settlement
  (70/20/10 split)
```

**Why this shape:**
- The API layer is thin — it validates input and delegates to `services.py`.
- `services.py` owns every balance mutation. There is exactly one code path that debits a merchant and exactly one that credits back on failure. This makes auditing trivial.
- Celery is a genuine async worker, not a sync shim. The `process_payout` task runs outside the request cycle, and `on_commit` ensures the task is only dispatched after the payout row actually exists in the database.

## Money integrity

### Why BigIntegerField in paise

All amounts are stored as `BigIntegerField` — the number of paise (1/100 of a rupee). No `FloatField`, no `DecimalField`.

**The reasoning:**
- Floats are fundamentally broken for money. `0.1 + 0.2 != 0.3` in IEEE 754. In a ledger, a sub-paise rounding error compounds into a balance that doesn't reconcile. This is not theoretical — it's the #1 source of accounting bugs in early-stage fintech code.
- DecimalField is safe mathematically, but paise-as-integer is simpler. There's no scale/precision to configure, no risk of someone passing `Decimal('1000.005')` and silently truncating. An integer is an integer — it either fits or it doesn't.
- The frontend converts rupees → paise before sending (`rupees * 100`, integer arithmetic). The display layer converts back. The entire backend never sees a decimal point.

### Why database-level balance, not Python

The balance is computed by a single SQL aggregate:

```sql
SELECT COALESCE(SUM(
    CASE WHEN entry_type='CREDIT' THEN amount_paise
         WHEN entry_type='DEBIT'  THEN -amount_paise
    END
), 0) FROM ledger_entries WHERE merchant_id = %s
```

This is generated by Django ORM in `services._compute_balance()` using `Sum(Case(When(...)))`.

**Why this matters:**
- If you fetch rows into Python and sum them, you have a TOCTOU problem. Between your `SELECT` and your `INSERT` of the debit, another transaction can insert a debit too. Both see sufficient balance, both debit, and the merchant goes negative.
- Even with locking (which we also use), doing the sum in SQL means the database engine itself is computing the number. There's no intermediate Python list of amounts that could be stale, truncated, or accidentally converted to float by a careless `sum()`.
- The aggregate runs against the same locked snapshot that the debit will write to. There's no window for divergence.

### The ledger invariant

```
available_balance = SUM(all CREDIT entries) - SUM(all DEBIT entries)
```

This is the single source of truth. There is no cached `balance` column on the merchant. If you run `_compute_balance()` at any point, you get the correct answer — even if the server crashed mid-payout.

When a payout is created → DEBIT entry immediately. If the payout fails → CREDIT entry returns the funds. If the payout succeeds → the DEBIT stands. The ledger is append-only; we never update or delete entries.

## Concurrency: the two-60-rupee problem

> A merchant with ₹100 balance submits two simultaneous ₹60 payout requests. Exactly one should succeed.

This is the classic check-then-act race condition. Here's how it's prevented:

### The lock: SELECT FOR UPDATE

In `services.create_payout()`:

```python
with transaction.atomic():
    merchant = Merchant.objects.select_for_update().get(id=merchant_id)
    balance = _compute_balance(merchant.id)
    if balance < amount_paise:
        return 422, {"error": "Insufficient funds", ...}
    # ... create payout + debit entry
```

`select_for_update()` acquires a **row-level exclusive lock** on the merchant row in PostgreSQL. This means:

1. Request A arrives, enters the transaction, locks the merchant row.
2. Request B arrives, enters its transaction, tries to lock the same row — **blocks**.
3. Request A computes balance (10000p), sees it's >= 6000p, creates the debit, commits. Lock released.
4. Request B unblocks, computes balance (now 4000p), sees it's < 6000p, returns 422. No debit created.

**Why lock the merchant row, not the ledger entries?**
- Locking individual ledger rows doesn't prevent new inserts — another transaction can insert a debit for the same merchant without touching existing rows.
- The merchant row acts as a serialization point. All operations that affect a merchant's balance must acquire this lock first, creating a total ordering of balance-mutating operations for that merchant.
- Different merchants are not affected — their rows are different, so concurrent payouts for different merchants proceed in parallel.

### Why not application-level locking (Redis, in-memory)

Application locks (Redis SETNX, Python threading locks) don't survive across processes, don't participate in the database transaction, and create a distributed coordination problem. If the app crashes while holding a Redis lock, you need a TTL-based fallback that can still allow duplicate processing.

`SELECT FOR UPDATE` is tied to the PostgreSQL transaction. If the process crashes, PostgreSQL rolls back the transaction and releases the lock automatically. No orphaned locks, no TTL tuning, no split-brain.

## Idempotency

### The problem

Network retries, client bugs, and load balancers can cause the same `POST /api/v1/payouts/` to arrive twice. Without idempotency, the merchant gets debited twice.

### The solution

The client sends an `Idempotency-Key` header (a UUID). The server:

1. **Inside the same transaction** that locks the merchant, checks if this (key, merchant) pair exists in `idempotency_keys` and was created within the last 24 hours.
2. If yes → return the cached `response_status` and `response_body`. No new payout created.
3. If no → proceed with normal payout creation, then store the response keyed to this idempotency key.

**Critical detail:** The idempotency check is inside the `SELECT FOR UPDATE` lock on the merchant row. This prevents a race where two requests with the same key both see "no existing key" and both create payouts. The lock serializes them — the second request will always see the key that the first one created.

### Key scoping and expiry

Keys are scoped per merchant (a `UNIQUE(key, merchant)` constraint). Merchant A's idempotency key `abc-123` doesn't conflict with Merchant B's `abc-123`.

Keys expire after 24 hours — the lookup filters by `created_at >= now() - 24h`. After expiry, the same key can be reused (which is correct — if you're retrying after 24 hours, something else went wrong and a new payout is likely intended).

## State machine

### Legal transitions

```
PENDING ──▶ PROCESSING ──▶ COMPLETED
                       └──▶ FAILED
```

No other transitions are allowed. The `Payout.transition_to()` method enforces this:

```python
VALID_TRANSITIONS = {
    'PENDING':    {'PROCESSING'},
    'PROCESSING': {'COMPLETED', 'FAILED'},
}

def transition_to(self, new_status):
    allowed = self.VALID_TRANSITIONS.get(self.status, set())
    if new_status not in allowed:
        raise ValueError(f"Illegal transition: {self.status} -> {new_status}")
    self.status = new_status
```

`COMPLETED` and `FAILED` are terminal — they have no entries in `VALID_TRANSITIONS`, so any transition from them raises `ValueError`.

### Why enforce at model level

Putting the constraint in the model (not just the view or task) means every code path — API, Celery task, management command, Django shell — goes through the same check. You can't accidentally move a completed payout back to pending from a debug script.

### Atomic fund return on failure

When a payout fails, the state transition and the fund-return CREDIT entry happen in the same `transaction.atomic()` block:

```python
with transaction.atomic():
    payout = Payout.objects.select_for_update().get(id=payout_id)
    payout.transition_to('FAILED')
    payout.save()
    LedgerEntry.objects.create(
        merchant_id=payout.merchant_id,
        entry_type='CREDIT',
        amount_paise=payout.amount_paise,
        ...
    )
```

If the CREDIT insert fails for any reason, the entire transaction rolls back — the payout stays in PROCESSING rather than moving to FAILED without returning funds. This is the atomicity guarantee that prevents "money disappearing" bugs.

## Retry logic

### The flow

1. `process_payout` task transitions PENDING → PROCESSING, simulates bank settlement.
2. 70% of the time: SUCCESS → COMPLETED. Done.
3. 20% of the time: FAILURE → FAILED + return funds. Done.
4. 10% of the time: HANG — task returns without settling. Payout stays PROCESSING.
5. Celery Beat runs `check_stuck_payouts` every 10 seconds.
6. For each PROCESSING payout past its backoff window:
   - If `attempts < 3`: dispatch another `process_payout` task.
   - If `attempts >= 3`: move to FAILED and return funds.

### Exponential backoff

```
Attempt 1: retry after 30s
Attempt 2: retry after 60s  (30 × 2¹)
Attempt 3: retry after 120s (30 × 2²)
After attempt 3: fail permanently, return funds
```

The backoff is calculated as `30 * 2^(attempts - 1)`. The periodic task compares `now()` against `last_attempted_at + backoff` to decide if it's time to retry.

### Why the periodic task, not Celery's built-in retry

Celery's `self.retry(countdown=...)` retries within the same task chain. But if the worker process crashes or the message is lost, the retry never fires. The periodic `check_stuck_payouts` task is a **sweep** — it catches any payout that's been stuck, regardless of why. It's the safety net that makes the system self-healing.

### Idempotent retries

The `process_payout` task handles both initial processing (PENDING → PROCESSING) and retries (already PROCESSING → re-simulate). If a retry races with the original task completing, `SELECT FOR UPDATE` ensures only one proceeds — the loser sees the payout is already in a terminal state and exits early.

## Frontend design

### Polling for live updates

The dashboard polls every 3 seconds for balance, payouts, and ledger entries. This gives near-real-time status updates as payouts move through states (you can watch a payout go from PENDING → PROCESSING → COMPLETED/FAILED).

I chose polling over WebSockets because:
- It's simpler to implement and debug.
- The data changes every few seconds, not milliseconds — 3s polling is effectively "live" for this use case.
- There's no connection management, reconnection logic, or state synchronization to get wrong.

### Integer-only display

The `formatINR()` function converts paise to display rupees using integer arithmetic:

```javascript
const rupees = Math.floor(paise / 100);
const paisePart = paise % 100;
return `₹${rupees.toLocaleString("en-IN")}.${String(paisePart).padStart(2, "0")}`;
```

No division that could produce floating-point artifacts. `Math.floor` and `%` on integers produce integers.

## What I'd do differently in production

1. **Authentication**: Merchant identity from JWT/session, not a `merchant_id` in the request body. The current design trusts the client to identify itself, which is only acceptable for a demo.

2. **Database migrations for the idempotency key expiry**: A periodic cleanup job that deletes keys older than 24h, plus a partial index on non-expired keys to keep the lookup fast.

3. **Webhook notifications**: Instead of polling, fire webhooks to the merchant when payout status changes. The frontend would also use WebSockets or SSE for the dashboard.

4. **Actual bank integration**: Replace the random simulation with a real NEFT/IMPS/UPI API. The settlement would be async — the bank sends a callback, and a webhook handler processes it.

5. **Audit log**: Every state transition logged with timestamp, actor, and reason. The current ledger covers financial mutations, but operational events (who triggered the retry, why it failed) need their own trail.

6. **Read replicas for balance queries**: The `GET /balance` endpoint doesn't need to hit the primary. Only the payout creation path needs the primary (for the lock).

7. **Dead letter queue**: Payouts that fail after max retries should land in a DLQ for manual review, not just be marked FAILED. In production, a stuck payout might indicate a bank outage, not a permanent failure.

8. **Rate limiting**: Per-merchant rate limits on payout creation to prevent abuse.

## Known limitations of this implementation

- **No auth**: Any client can create payouts for any merchant. This is intentional for the demo — adding auth would obscure the payout logic that's being evaluated.
- **Single-process Celery**: The docker-compose runs one worker with 4 threads. Production would use multiple workers across multiple hosts.
- **No monitoring**: No Prometheus metrics, no structured logging, no alerting on stuck payouts. These are table stakes for production money-moving code.
- **Polling-based frontend**: Acceptable for a demo dashboard, but would not scale to thousands of concurrent viewers.
